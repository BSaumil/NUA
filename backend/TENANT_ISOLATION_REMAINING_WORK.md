# Tenant isolation — remaining work

Tracks progress against the audit's finding that 38 of 58 backend route files had zero `businessId` scoping. This file exists so the remaining gap is recorded precisely rather than silently left implicit — per the Trust Release directive, "record the exact blocker and continue."

JWT membership is now authoritative; the header is only consulted when there's no JWT at all (the original partner-integration use case). |

| `routes/hq.py` | Explicitly a cross-location feature by design (franchise/brand roll-ups via `businesses.parentBrandId`) — but none of its 4 endpoints ever checked which brand a location belonged to. `/kpi-roll-up` and `/leaderboard` aggregated `db.transactions` across literally every business on the deployment with no filter at all, so any logged-in staff member could see every *unrelated* tenant's revenue, covers, and GST, not just sibling locations under their own brand. `/brands` and `/locations` had the same gap for the business directory itself. Fixed with `_brand_scope_business_ids()`, which resolves the caller's own brand root plus every location under it, and scopes all four endpoints to that set — this is the one file in this pass where the fix is deliberately NOT the usual single-business `tenant_scope_filter` pattern, since the feature's entire purpose is seeing *multiple* locations, just only the caller's own group of them. |
| `routes/reservations.py` (floor-plans section only) | **Not one of the audit's original 34 files** (this file was presumably assessed as already-scoped) — found while investigating whether `table_courses.py`'s `table_states` collision risk extended to floor-plan table ids. | `routes/table_courses.py` | `table_states` (live floor-plan seating/course state) and `dock_notifications` (the "Send" nudge log) were keyed with no `businessId` at all — worse than a read leak: `table_states` is looked up only by `tableId`, so two businesses on a shared deployment both seating "Table 5" collided on one document (one business's course/guest-name/VIP data could be silently overwritten by the other seating a same-numbered table, and one clearing their table could clear the other's). Both scoped now; `table_course_settings` (a `_id: "singleton"` doc) deliberately left global, same architectural gap as `business_settings`. `services/table_pacing.py` and `services/ticket_lifecycle.py` also touch `table_states` directly by a resolved internal floor-plan table id (not the raw client-supplied `tableId` string this fix addresses) — plausibly already collision-safe since that id is resolved through `floor_tables.resolve_table()`, which is presumably itself business-scoped, but this wasn't independently verified and is worth confirming in a future pass. |
| `routes/awards.py` | Another zero-auth finding, and a compliance-sensitive one: all 6 endpoints (`catalogue`, `install`, `installed`, `uninstall`, `sync-fairwork`, `payruns/super-by-award`) had no `Depends` at all — any authenticated user of any role/business could install or uninstall Fair Work awards, and `db.awards` was keyed only by `code` (e.g. `"MA000119"`, a shared national identifier), so two businesses installing the same award collided on one document — business A uninstalling it silently uninstalled it for business B too. Fair Work award data feeds directly into `super-by-award`'s superannuation-contribution calculation, so this wasn't just a data leak. Auth added (`require_owner_or_manager` for install/uninstall/sync, `get_user` for reads); `db.awards` re-keyed to `(code, businessId)` so each business's install state is independent. |
| `services/entity_service.py` (root cause) + `routes/measured_inventory.py` | **The single highest-impact fix in this whole pass.** `_stamp_new()` used `doc.setdefault("businessId", ctx.get("businessId"))` — but every `BaseEntity`-derived model (and `Product` specifically) declares `businessId` as a real field defaulting to `None`, so a caller that builds a full model instance and passes `model.dict()` into `stamped_insert` already has an explicit `"businessId": None` key. `setdefault` is a no-op against an *existing* key, even a `None` one, so the actor's real businessId was never applied. Confirmed victim: `routes/products.py`'s `create_product` — **every product ever created via `POST /api/products` was stamped with `businessId=None`, regardless of who created it**, making every business's entire product catalogue (cost, stock, pricing) universally visible to every other business through `tenant_scope_filter`'s "missing/null = visible to everyone" backward-compat default. `services/menu_features.py`'s bulk-import and `services/alcohol_seeder.py`'s seeding write "products" through the same path and were equally affected. Fixed at the root: `_stamp_new` now overwrites a falsy `businessId`/`locationId` instead of only filling in a missing key — this fixes every current and future caller of `stamped_insert`, not just products. `routes/measured_inventory.py` (11 endpoints across `stock_units`/`sell_variants`/`open_containers`/`wastage_events`) was scoped transitively through `db.products` at the same time — those four collections' own writes were NOT hit by the `_stamp_new` bug (their `...Create` request models have no `businessId` field, so the key was genuinely absent, not explicit-`None`), but nothing had ever filtered a *read* by tenant either, so margin/cost/wastage data was fully cross-tenant readable regardless. |

| `services/approval_service.py` + `routes/approvals.py` | Zero businessId scoping anywhere — `enqueue_approval` never stamped one, and `list_approvals`/`pending_count`/`get_approval`/`approve`/`reject` had no tenant filter at all. **Severe**: every pending high-risk approval on the whole deployment (refunds over threshold, purchase orders, marketing campaigns, VIP tier downgrades, Ash agent tool calls awaiting sign-off) was visible to, and — via `/approve`/`/reject` — actionable by, any owner/manager of *any* business, not just their own. Fixed at the root, same pattern as `notification_service.send()`: `enqueue_approval` now defaults `business_id` from the current request's actor context when a caller doesn't pass it explicitly (none of the 3 call sites — `routes/nua.py`'s marketing-campaign approval, `services/nua_tools.py`'s agent-tool gate, `services/rules_engine.py`'s rule-action gate — do), so all 3 are fixed without editing them individually. Routes scoped/owned-checked accordingly (approve/reject return 404, not 403, for a non-owned approval — consistent with the rest of this pass's not-found-over-forbidden convention for cross-tenant resource access). |

| `routes/advanced_features.py` | Wide-surface file (818 lines) with several distinct findings. `POST /tips/add` had **no `Depends` at all** — any valid staff token, any business (or, per the earlier systematic missing-`Depends` sweep, this one had already been flagged as "reachable with *some* token but no route-level check" — confirmed here it actually had none at all in the signature) could log a tip against any business with no businessId stamped. `GET /tips`, `/tips/summary`, `/tips/pool-distribute` all read `db.tips` with zero tenant filter — one business's tip ledger (and per-staff earnings) was visible to every other business, and pool-distribute paid out pooled tips **across every business's active staff on the deployment**, not just the caller's own — a genuine cross-tenant financial-integrity bug, not just a leak. `GET /reports/end-of-day` aggregated `db.transactions`/`db.refunds`/`db.tips`/`db.customers` with no filter — every business's End-of-Day revenue, refunds, tips and customer analytics were mixed into whichever business ran the report. All scoped/stamped/owned-checked now. `/business/settings`, `/business/theme`, `/pos/layout`, `/settings/training-mode` intentionally left as the pre-existing singleton-document architectural gap (same as `business_settings`/`print_routing` elsewhere), not fixed here. **A bug caught during this fix, not shipped**: the first draft of the segment-customer scoping used `query.update(tenant_scope_filter(...))`, which silently clobbered `_build_segment_query`'s own `$or` clause (used by the `inactiveForDays` rule) since both used the same top-level `"$or"` key — this would have made "hasn't visited in N days" match every customer in the business instead of just the inactive ones. | `routes/ai_pantry.py` | Zero businessId scoping across `pantry_lists`, `invoices`, and the reads feeding `generate_pantry_list`/`product_insights` (`products`, `transactions`, `reservations`). **The sharpest finding**: `parse_invoice` matched a supplier invoice's line items against *every* business's product catalogue (not just the uploader's own), and `apply_invoice` then wrote the resulting price/cost update straight to `db.products` with no ownership check at all — a business could reprice another business's products via the invoice-OCR flow. ## A deeper, separate finding surfaced while fixing payroll/gamification/preshift

`timecards`, `shifts`, and `roster_shifts` documents don't carry a `businessId` field at all — not just unfiltered queries, the schema itself has no tenant tag on these three collections. The fix applied here (filter transitively through the calling business's own `auth_users` staff list) closes the isolation gap without a migration, but it's worth flagging as its own item: any *other* code path that queries these three collections directly by some key other than a pre-filtered staffId list would still need the same transitive-filter treatment, since there's no `businessId` on the document itself to scope by directly.

`db.business_settings` and `db.settings` (used for e.g. print-routing config) are **singleton documents** (`{"key": "main"}` / `{"key": "print_routing"}`) with no per-tenant scheme whatsoever — every business on this deployment currently shares one ABN/business-name/GST-settings record and one print-routing config. This is a real architectural gap, but re-keying these collections by businessId touches enough call sites (business_settings alone is read in `payroll.py`, `advanced_features.py`, and elsewhere) that it deserves its own dedicated migration task rather than a rider on this pass.

## A systematic check worth recording: is the bill_split.py auth gap a one-off or a pattern?

After finding three unauthenticated "staff" endpoints hiding behind the `/api/table/` public prefix, every route across the codebase whose path matches one of server.py's `PUBLIC_API_PREFIXES` (`/api/public/`, `/api/table/`, `/api/online/orders/track/`, `/api/waitlist/track/`, `/api/v25/kiosk/session/`, the three `/api/voice/...` Twilio callback paths) was enumerated and read. `routes/bill_split.py`'s three were the only genuine mismatch — the rest (`public.py`, `table_ordering.py`, the two `track/` endpoints, the kiosk session endpoint, the Twilio callbacks) are all intentionally public by design and consistent with their own docstrings/naming. Recorded here so this doesn't need re-deriving: it was a real but isolated bug, not a systemic one.

## A completed systematic sweep for the same bug class (missing `Depends` entirely)

A regex scan across every route in the 30 remaining files for a signature with no `Depends(...)` anywhere in it turned up ~65 matches. Triaged all of them:

- The large majority are legitimately public by design — under a `PUBLIC_API_PREFIXES`/`PUBLIC_API_PATHS` entry (guest storefront, kiosk, QR table ordering, webhooks with their own signature verification, health checks) — consistent with their own naming/docstrings.
- `routes/repo_sync.py`'s `/status` and `/run` are a **false positive of the scan method**: they auth manually inside the function body (`get_current_user(request)` + an owner-only role check) rather than via a `Depends(...)` in the signature, which the regex can't see. No issue.
- `routes/licensing.py`'s `/validate` is not in the public allowlist, so the global `RequireAuthMiddleware` already requires a valid staff token to reach it — the opposite problem from a security gap: its own docstring says it's meant to be called by a POS device *before* anyone has logged in, so it may currently be *non-functional* for that bootstrap case rather than insecure. A functional bug, not a vulnerability — flagged here, not fixed (out of scope for this security pass).
- No other instance of the true "reachable with zero credential at all" bug class (the `bill_split.py`/`awards.py` pattern) was found in this sweep. The remaining ~15 matches not covered above are routes that DO require a valid staff token via the global middleware but have no *route-level* role/tenant check beyond that (e.g. `advanced_features.py`'s `/tips/add`, `bookings_inbox.py`'s ingest/ack/dismiss, `channel_menus.py`, `loyalty.py`'s rewards/events, `reservation_features.py`'s table-combinations/schedule/club-offers, `v25_suite.py`'s sync-queue/hardware-heartbeat/dynamic-pricing/subscriptions) — lower severity than a true zero-auth gap (an attacker needs SOME valid staff credential, not none at all), but still worth the normal tenant-scoping pass each of these files needs regardless, per the recommended order above.

**Worth a dedicated follow-up, not scoped here:** now that `_stamp_new`'s root-cause businessId bug is fixed, it's worth grepping the codebase for every model that extends `BaseEntity` (or otherwise declares an explicit `businessId: Optional[str] = None` field) and is constructed as a full model instance before being passed to `stamped_insert`, to confirm `products` was the only *currently-read* collection affected — `menu_features.py` and `alcohol_seeder.py` both write "products" through the same bug and are already covered by the fix, but a systematic check would catch any other collection with the same construction pattern that this pass didn't specifically go looking for.

Plus the remaining endpoints in `routes/finalize.py` itself: booking day-rules, channel state/schedule, low-stock PDF/XLSX export, AI-pantry order-sheet PDF, automation triggers.

Some of these are legitimately public/unauthenticated by design (`public.py`, parts of `guest_session.py`) where "tenant scoping" means something different (scoping by the resource being looked up, not by a staff JWT) — those need a case-by-case read, not a mechanical copy of the `tenant_scope_filter` pattern used above.

**Recommended order for the next pass**, ranked by the same "real PII/financial data first" logic used for this one: `measured_inventory.py`/`awards.py` (stock/cost data — margin-sensitive), `reservation_features.py`/`table_courses.py`/`table_ordering.py` (booking/guest data, same family as the kitchen.py fix), `hq.py` (explicitly a cross-location feature — needs care to scope "correctly restricted" without breaking its actual purpose), then the rest. Given the severity of what turned up in `bill_split.py`, it's also worth a second full sweep — same method as "A systematic check" above — of every route in the 32 remaining files for a *missing* `Depends` entirely (not just a missing tenant filter on an otherwise-authenticated route), since that class of bug is worse than anything "tenant scoping" alone addresses and wasn't the original audit's specific focus.
