1  ·  ONE-LINE PITCH & POSITIONING
────────────────────────────────────────────────────────────────────────────────

NUA is an AI-powered Hospitality Operating System for restaurants, cafés,
bars, quick-service outlets, dark kitchens, retail concepts, and franchised
groups. It fuses point-of-sale, reservations, kitchen display, inventory,
enterprise finance, payroll, CRM, loyalty, marketing, and a full autonomous
AI operating layer ("NUA / Ash") into one system driven by a single source
of truth and one universal event stream.

Positioned against    : Toast, Square for Restaurants, Lightspeed Restaurant,
                        SevenRooms, OpenTable, Deliverect, Xero + POS combos.
Differentiator        : Autonomous AI agent that plans, predicts, and executes
                        with a human-in-the-loop approval queue.

2  ·  PRODUCT PRINCIPLES (CONTRACT)
────────────────────────────────────────────────────────────────────────────────

  2.1  Single Source of Truth
       Every module — POS, Reservations, Kitchen, Payroll, Accounting,
       Inventory, CRM, Marketing — reads and writes to one shared customer,
       product, ingredient, staff, and financial database.

  2.2  Total Traceability
       Every action (human or AI) writes an immutable audit event: who,
       when, from what device, from what IP, at what location, on which
       business. Every entity has full version history and can be restored
       to any prior state.

  2.3  AI Recommends → Owner Approves → System Automates
       NUA never performs high-risk actions (large POs, refunds, tier
       downgrades, mass discounts) without explicit owner approval.
       Low-risk actions (docket notifications, minor stock updates, notes)
       are fully automated.

  2.4  Multi-Site by Design
       Every record carries `businessId` + `locationId`. Franchises
       (brand → franchisee → location) are first-class citizens. HQ
       dashboards roll up across the network.

  2.5  Right To Be Forgotten
       Soft-delete first. Hard-delete is an owner action that also purges
       audit/version history for GDPR compliance.

  2.6  Explainable AI
       Every AI decision persists six explainability fields: problem,
       evidence, confidence, alternatives, risk, expected impact, rollback.

5  ·  UNIVERSAL ENTITY MODEL (CONTRACT)
────────────────────────────────────────────────────────────────────────────────

Every top-level entity extends BaseEntity:

  Field            Purpose
  ────────────────────────────────────────────────────────────────
  id               UUID v4
  businessId       Tenant / brand
  locationId       Physical outlet (nullable for HQ-level entities)
  createdBy        User email or `system:<subsystem>`
  createdAt        ISO-8601 UTC
  updatedBy        User email or `system:<subsystem>`
  updatedAt        ISO-8601 UTC
  deletedAt        Soft-delete tombstone
  deletedBy        Who soft-deleted
  device           Client user-agent snapshot
  ip               Request IP
  version          Monotonic counter — bumps on every update

Tracked entity kinds:
  customer, product, ingredient, recipe, supplier, purchase_order, booking,
  table, employee, device, kitchen_ticket, voucher, wallet, loyalty_transaction,
  payment, refund, journal_entry, bill, invoice, rule, audit_event, ash_plan,
  ash_memory, badge, milestone, challenge, docket_config

MongoDB safety rules:
  • Never return raw MongoDB docs — always coerce _id → id via PyObjectId /
    from_mongo() helpers.
  • datetime.now(timezone.utc) — never datetime.utcnow().
  • Use `stamped_insert` and `stamped_update` from utils/entity_service.py so
    every write auto-populates version, updatedBy, device, ip, and emits an
    audit event.

6  ·  NUA / ASH — THE AUTONOMOUS OPERATING LAYER
════════════════════════════════════════════════════════════════════════════════

NUA (rebranded from "Ash") is the always-on AI agent that observes, analyses,
plans, and executes across every module. It is the single most differentiated
part of the product.

6.1  ─  Persona Registry (6 identities)                    services/ash_personas.py
──────────────────────────────────────────────────────────────────────────

  ID          Label            Modules                                Voice
  ─────────────────────────────────────────────────────────────────────────────────
  executive   Ask NUA          all                                    warm, terse,
                                                                      strategic
  finance     NUA Finance      Finance, Ash                           precise, sceptical
  ops         NUA Ops          Inventory, Ash                         hands-on, direct
  hr          NUA HR           Staff, Ash                             empathetic, coaching
  marketing   NUA Marketing    Marketing, Customers, Ash              creative, growth
  guest       NUA Guest        Customers, Reservations, Ash           warm, hospitality

  • Executive is default; represents the merged "Ask NUA" chat experience.
  • Each persona filters the visible tool catalog by module. Tools outside
    remit are refused with a "switch to persona X" suggestion.
  • System prompt is wrapped per persona to shape tone + focus.

6.2  ─  Tool Catalog (25 tools)                                services/ash_tools.py
──────────────────────────────────────────────────────────────────────────

  Every tool has: name, label, module, risk (low|medium|high|critical),
  defaultPermission (auto|approval|disabled), and an execute() function.

  Read-only  : fetch_open_insights, fetch_kpis, lookup_customer,
               lookup_product, run_ash_scan, generate_daily_briefing, recall,
               list_pending_approvals, get_health_score
  Low-risk   : add_customer_note, create_task, remember
  Mid-risk   : create_purchase_order, adjust_menu_price, issue_voucher,
               cancel_reservation, credit_wallet, send_sms, send_email
  High-risk  : issue_refund, bulk_promotion, tier_downgrade,
               approve_pending_approval, reject_pending_approval

  Permission gate:
    • auto      → executes immediately, audit-logged
    • approval  → enqueues in db.approvals for owner review
    • disabled  → refused with an explanation

  Owner controls each tool's effective permission via
    PUT /api/nua/tools/{name}/permission
  Managed in UI at /ash-permissions (page: AshPermissions.jsx).

6.3  ─  Multi-Turn Agent Loop                                    services/ash_agent.py
──────────────────────────────────────────────────────────────────────────

  run_agent_turn(message, sessionId, actor, persona):
    1. Load grounding context (last 15 audit rows, 10 open insights,
       10 pending approvals, memory pack).
    2. Wrap AGENT_SYSTEM prompt with persona voice.
    3. Loop up to MAX_TURNS (4):
         a. Call GPT-5.2 via emergentintegrations.
         b. Parse strict JSON envelope {action, tool, args, reasoning}.
         c. If tool_call → execute (or gate to approval), append result,
            iterate.
         d. If final → break.
    4. Persist result + trace in db.ash_agent_log.
    5. Return { reply, reasoning, toolResults, trace, persona, personaLabel }.

  Robust JSON parsing: markdown-fence stripping, balanced-brace matching,
  newline sanitisation, regex last-resort — the {"action":"final",...}
  envelope can never leak into user-visible replies.

6.4  ─  Long-Term Memory                                       services/ash_memory.py
──────────────────────────────────────────────────────────────────────────

  Collections   db.ash_memories, db.ash_memory_summary
  Shape         { id, scope, kind, text, confidence, source, tags,
                  usageCount, createdAt, updatedAt, lastUsedAt }
  Kinds         preference | pattern | fact | note
  Scopes        global | customer:<id> | staff:<id> | product:<id> |
                supplier:<id>
  API           GET /api/nua/memory · POST /api/nua/memory
                GET /api/nua/memory/scopes · DELETE /api/nua/memory/{id}
  UI            /ash-memory (page: AshMemory.jsx)
  Reinforcement Same (scope,text) upserts with +0.1 confidence per repeat
                (max 1.0).
  Injection     context_pack(scope) is auto-appended to every agent turn.

6.5  ─  Planning Engine                                      services/ash_planner.py
──────────────────────────────────────────────────────────────────────────

  A "plan" is a multi-step tool-backed proposal. Owner approves the whole
  plan or individual steps; each step still respects the tool-permission
  gate.

  Lifecycle     proposed → executing → awaiting_approvals → completed
                (or partial_failed, rejected)
  Steps         [{ tool, args, rationale, status, outcome, approvalId }]
  API           POST /api/nua/plans/generate { goal, persona? }
                GET  /api/nua/plans (list)
                GET  /api/nua/plans/{id}
                POST /api/nua/plans/{id}/approve       (walk all pending)
                POST /api/nua/plans/{id}/reject
                POST /api/nua/plans/{id}/steps/{idx}/approve
                POST /api/nua/plans/{id}/steps/{idx}/reject
                POST /api/nua/plans/{id}/simulate      (dry-run + LLM narrative)
  UI            /ash-plans (page: AshPlans.jsx) — simulate button before Approve

6.6  ─  Digital Twin (Plan Simulation)                    ash_planner.simulate_plan
──────────────────────────────────────────────────────────────────────────

  Dry-runs a plan:
    • Read-only tools ACTUALLY execute (grounding data is real).
    • Write tools are DESCRIBED — no db mutation, no approvals enqueued.
    • GPT-5.2 authors a projected-outcome narrative (revenue, cost, CSAT,
      risks).
  Owners see this in the AshPlans page as an "Simulate first" button —
  a safety net before Approve & walk.

6.7  ─  Health Score                                          services/health_score.py
──────────────────────────────────────────────────────────────────────────

  A 0-100 composite scored hourly by the Ash Scheduler:
    Revenue delta vs. baseline
    Margin health
    Stock coverage days
    Staff burnout signals
    Guest satisfaction proxy (feedback + waitlist)
    Compliance gaps (missing invoices, un-reconciled cash)
  Displayed at /ash-hq as a live gauge with per-dimension drivers.

6.8  ─  Ash Scheduler (background jobs)                     services/ash_scheduler.py
──────────────────────────────────────────────────────────────────────────

  Hourly    Recompute health score, refresh open insights.
  Daily     Generate morning briefing (short LLM narrative + KPI card).
  Weekly    Long-form business summary + strategic recommendations.
  Ad-hoc    /api/nua/agent invocations from AshChat FAB.

6.9  ─  Approval Queue                                     services/approval_service.py
──────────────────────────────────────────────────────────────────────────

  Any action that meets a policy threshold is enqueued instead of firing.
  Defaults (env-configurable):
    AI_APPROVE_PO_ABOVE=500        POs over $500
    AI_APPROVE_REFUND_ABOVE=100    Refunds over $100
    AI_APPROVE_TIER_DOWNGRADES=1   Any downgrade
    AI_APPROVAL_MODE=thresholds|strict|off
  UI          /approvals (page: Approvals.jsx)
  Shape       { id, actionType, payload, confidence, reasoning, status,
                requestedBy, requestedAt, decidedBy, decidedAt }

6.10 ─  Ash Insights                                         services/ash_intelligence.py
──────────────────────────────────────────────────────────────────────────

  Sixteen continuous jobs write into db.ash_insights:
    1. Staffing shortages (roster vs forecasted covers)
    2. Theft (comp/void anomalies)
    3. Fraud (card mismatches, refund velocity)
    4. Pricing recommendations (margin decay)
    5. Promotions on slow inventory
    6. Food waste (pull rate vs stock aging)
    7. Labour cost anomalies (wages ÷ revenue by shift)
    8. Menu underperformance (Menu Engineering drift)
    9. Weather impact forecast
    10. Public holiday demand forecast
    11. Purchasing recommendations (par + lead time + forecast)
    12. Roster recommendations (sales forecast vs rostered hours)
    13. Staff burnout prediction
    14. Customer churn prediction (days-since-visit vs tier norm)
    15. Menu Engineering (Star / Puzzle / Plow-Horse / Dog quadrants)
    16. Auto weekly summary (LLM narrative over KPIs)

  Each insight persists severity + recommendedActions[] + optional
  approvalLink.

8  ·  SECURITY & COMPLIANCE
════════════════════════════════════════════════════════════════════════════════

8.1  Authentication
     • JWT via /api/auth/login (email + password).
     • Optional 4-digit PIN for POS shift-swap.
     • bcrypt password hashing (never MD5 / SHA1).
     • Emergent Google OAuth ready.
     • Rate limiting (RateLimitMiddleware) — 60 req/min per IP.
     • Brute-force lockout after 5 failed logins in 5 min.

8.2  Authorisation
     • Roles: owner · manager · cashier · kitchen · marketing · read-only.
     • Every write endpoint uses Depends(get_user) or Depends(require_*).
     • Owner-only actions include: license changes, tool permissions,
       hard delete, payroll finalisation, tax settings.

8.3  Auditability
     • ActorContextMiddleware stamps every write with actor + IP + device.
     • Immutable audit trail (no updates or deletes on audit_logs).
     • Version counter on every entity for point-in-time restore.

8.4  Data Protection
     • Soft-delete tombstones; owner triggers hard-delete + audit-purge for
       GDPR right-to-be-forgotten.
     • PII fields flagged and redacted in logs.
     • PCI: card data never touches NUA — Stripe.js tokenises client-side.

8.5  Approvals
     • Every high-risk AI or user action routes to Approvals with a
       confidence + reasoning payload.
     • Owner can require ALL AI actions to be approved by setting
       AI_APPROVAL_MODE=strict.
